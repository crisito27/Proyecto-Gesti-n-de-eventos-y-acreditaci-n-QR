# Evidencias pendientes que requieren al equipo

Este archivo no reemplaza las evidencias reales. Es una lista de verificación
para completar antes de la entrega.

## 1. Evidencia de diseño previo

El enunciado exige demostrar que la interfaz fue pensada antes de implementarse.
El repositorio ahora incluye `docs/diseno-interfaz.md`, pero el equipo debe
aportar **una evidencia real y fechada** si existe.

Opciones válidas:
- captura de Figma con historial/fecha;
- foto de un wireframe dibujado previamente;
- archivo de diseño guardado antes o durante las primeras etapas;
- captura de una conversación o documento donde se definieron pantallas;
- commit temprano que contenga bocetos o documentación.

Guardar las imágenes en `taller2-react/docs/evidencias/` y enlazarlas desde
`docs/diseno-interfaz.md`.

## 2. Validación humana del reporte de IA

Abrir `docs/uso-ia.md` y revisar que:
- las herramientas nombradas sean las que realmente usaron;
- los prompts sean representativos;
- “modificación humana” describa acciones que el equipo efectivamente realizó;
- “aprendizaje” pueda ser explicado de memoria por quien lo presenta.

No declarar revisiones o aprendizajes que no ocurrieron.

## 3. Participación individual en GitHub

Cada integrante debe dejar evidencia real de colaboración. No conviene fabricar
commits históricos.

Antes de entregar, cada integrante debería realizar al menos una mejora real
desde su propia cuenta:
1. crear/usar una rama `feature/<tarea>`;
2. hacer un commit descriptivo;
3. subir la rama;
4. abrir Pull Request hacia `develop`;
5. otro integrante revisa y fusiona.

Tareas pequeñas pero reales que pueden repartirse:
- Ignacio: agregar evidencias de diseño y revisar documentación.
- Cristian: ejecutar el flujo completo y corregir texto/detalles detectados.
- Benjamin: revisar API/React y el reporte de IA.

## 4. Evidencias de prueba

Tomar capturas de:
- listado y filtros;
- validaciones del formulario;
- entrada QR;
- acreditación correcta;
- intento de segunda acreditación;
- dashboard;
- estado de API (datos y, si pueden, error/sin datos);
- vista móvil/responsive.

Estas capturas sirven para la presentación y como respaldo si algo falla en vivo.

## 5. Presentación oral

El equipo debe preparar quién explica cada sección y ensayar la demo completa.
Usar `docs/guia-presentacion-defensa.md` como pauta, pero cada integrante debe
entender el flujo completo porque las preguntas pueden ser individuales.
